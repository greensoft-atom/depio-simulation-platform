# Defect register

Every defect found since the audit of **2026-09-23**, each with an ID, and kept
after it is fixed as the record of what was wrong and what closed it. The
register was the input to [plan.md](plan.md)'s ordering — the roadmap was
re-ordered around it rather than the other way round. **As of 2026-10-04
nothing is open but M-6's three latent leftovers** (L, none reachable in play):
every other entry is fixed, closed as not a defect with its reason, or left as
it is by a stated choice (O-5).

**Ids.** P protocol (§2), D data and the result pipeline (§3), M simulation
(§3a), T concurrency (§4), S security and input (§5), O operations (§6), DOC
documentation (§7). A data defect is written "defect D-*n*" outside §3, because
the decision log numbers its decisions D-*n* too; inside this register a bare
D-*n* is a defect, and a decision is written "decision D-*n*".

**The second audit, 2026-10-01** ([Q-42](requirements/01-scope-and-nfrs.md#7-open-questions),
plan item 49), read what was built since the first by the same lenses: data,
concurrency, security and input, operations. Each candidate was checked against
the code before it was written down; 28 held, each in its section (D-32 to
D-39, T-32 to T-38, S-13 to S-19, O-6 to O-10, DOC-17), three of them H. Plan
items 50 to 60 fixed them, the worst first, the last on 2026-10-02.

**The review of 2026-10-04** (plan item 79) read everything built, code, scripts,
units and documents, module by module. 64 defects held and were fixed by the next day,
each in its section (P-38 to P-54, D-42 to D-51, M-17 and M-18, T-48 to T-57, S-20
to S-26, O-15 to O-31, DOC-21), seven of them H.

**How to read the Verified column.** `measured` means it was reproduced against
the running system (MySQL, a JVM run, a probe) during the audit. `read` means it
was established by reading the code and is mechanically obvious. `tested` means
a test reproduces it and holds the fix; `drill` or `drilled`, a live drill
against a release. Nothing here is a guess; where something is inferred rather
than reproduced, it says so.

Severity: **C** blocks a client or loses data · **H** wrong behaviour in normal
operation · **M** wrong behaviour in a reachable edge case · **L** latent.

## 1. The structural finding — **CLOSED 2026-09-25**

**Nothing decoded the snapshot encoder's output.** Not one test, not the bot
harness, not the golden vectors.

| Producer | Consumer | Verified against |
|---|---|---|
| `SnapshotCodec` (the spike) | itself | `vectors.txt` ✅ round-trips |
| `SnapshotReader.cs` (the client) | — | never compiled, never run ❌ |
| **`SnapshotEncoder` (the real server)** | — | **nothing** ❌ |

`SnapshotEncoderTest` asserts on encoder-*side* state — byte lengths, entity
counts, `ClientView` internals — and never parses a byte it produced.
`BotClient` reads the frame type and the leading `tickDelta` varint so it can
ack, then discards the rest. `vectors.txt` is generated by `SnapshotCodec`,
which is a **different encoder** from the one the server runs.

So the artefact that is supposed to bind the three implementations together
validates an encoder the server does not use. Every defect in §2 below —
P-1, P-2, P-3, P-4, P-5, P-6 — is invisible to the entire test suite, and one
test would have made all six impossible to miss.

**This is why the protocol work came first.** It is not the most severe defect;
it is the one that let the severe ones exist.

### How it was closed

Three links, and the chain now meets in the middle:

| Link | Where |
|---|---|
| The real encoder's bytes decode to the server's own state | `arena/SnapshotRoundTripTest` |
| That decoder reads the golden vectors | `protocol/GoldenVectorTest` |
| The byte encodings themselves are pinned at their boundaries | `protocol/WireFormatTest` |

`protocol.SnapshotReader` decodes a frame; `protocol.ClientWorld` accumulates
one into a handle table and world-space positions, and is the reference the Unity
client is a port of. The round-trip test drives a real `World` and `ClientView`
through the real `SnapshotEncoder` for hundreds of ticks and asserts that every
entity the client holds sits **exactly** where the server has it — with no
acknowledgements, with every frame acknowledged, and with the camera travelling.

`protocol/` went from 391 lines and zero tests to 19 tests. `common/` had none
then, and has had tests since 2026-09-26.

Five of the six defects the gap was hiding were found by running it. Each fix
below was confirmed by watching the test fail first.

could time out. Nothing shows it: `backend_store_connected` reads the command
connections only, the gateway has no measure of its subscription, nobody counts

## 8. What this changes

**As written on 2026-09-23. All three are resolved:** the protocol since
2026-09-25 (§1); the durability guarantees since 2026-09-25 (§3); and the
backend's lead over its consumer since the client's engine-free core was built
against the real server from 2026-09-27 (plan item 3,
[08 §7](detailed-design/08-client.md#7-order-of-work)), every feature since
driven end to end by its live drills.

Three conclusions the audit forces, in order.

**The protocol is not a contract yet.** Six client-blocking defects survive in
it because nothing decodes what the server sends. Any client work — by anyone,
in any language — would hit P-1 and P-3 on day one. Closing the loop is days of
work and it is the cheapest thing on this list.

**Three of the five durability guarantees do not hold.** Exactly-once, "a result
is never lost", and "every balance change goes through one path" each fail in a
reachable scenario, and two of them fail on a *planned restart* rather than a
crash. These were all stated as facts in documents and commit messages. They are
now stated as defects here until the code catches up.

**The backend is ahead of its consumer and the gap is compounding.** Every
feature added increases what a client must implement against a contract that has
never been executed end to end. That is the argument for the ordering in
[plan.md](plan.md#what-to-do-next-in-order).
