# 05 — Persistence with MongoDB

Only the **hub** process opens MongoDB connections. Arena processes get their
inputs via memstore tickets and emit outputs via memstore queues that hub
drains and persists. This keeps every slow or failing DB operation out of the
realtime path.

Driver: `org.mongodb:mongodb-driver-sync:3.12.x` (Java 8). Connection pool
size 32, `w: majority` is irrelevant on a single node — use `w: 1`,
`journal: true` for anything involving currency or inventory. Server:
MongoDB 4.4 or 5.0, WiredTiger cache capped (`storage.wiredTiger.engineConfig.cacheSizeGB: 8`).

## 1. Collections

### `players`

```json
{
  "_id": ObjectId,
  "v": 3,                                   // schema version
  "auth": { "username": "red", "pwHash": "argon2id$…", "createdAt": ISODate, "lastLoginAt": ISODate },
  "profile": { "name": "RedCarrot", "colorId": 4, "avatar": 2, "country": "KR" },
  "progress": { "accountLevel": 27, "accountXp": 15430, "rating": { "duel": 1420, "team": 1510 } },
  "wallet": { "coins": 12500, "gems": 40 },
  "inventory": [
    { "itemId": "eq_barrel_steel", "instanceId": "…", "qty": 1, "acquiredAt": ISODate },
    { "itemId": "boost_xp_2x_1h", "qty": 3 }
  ],
  "equipment": { "BARREL": "eq_barrel_steel", "ARMOR": null, "CORE": "eq_core_regen" },

```

Indexes: `{ "auth.username": 1 } unique`, `{ "teamId": 1 }`,
`{ "stats.bestScore": -1 }` (for offline leaderboard rebuilds), `{ "profile.name": 1 }`.

### `teams`

```json
{
  "_id": ObjectId, "v": 1,
  "name": "Pentagon Hunters", "tag": "PNT", "createdAt": ISODate,
  "leaderId": ObjectId,
  "members": [ { "playerId": ObjectId, "role": "LEADER" | "VICE_LEADER" | "MEMBER", "joinedAt": ISODate, "contrib": 1200 } ],
  "capacity": 30,
  "settings": { "joinPolicy": "OPEN" | "INVITE" | "APPROVAL", "minLevel": 5 },
  "stats": { "rating": 1500, "wins": 40, "losses": 22, "trophies": 3 },
  "invites": [ { "playerId": ObjectId, "byId": ObjectId, "at": ISODate } ],
  "applications": [ { "playerId": ObjectId, "at": ISODate, "msg": "" } ]
}
```

Indexes: `{ name: 1 } unique`, `{ tag: 1 } unique`, `{ "members.playerId": 1 }`,
`{ "stats.rating": -1 }`.

**Source of truth for membership is `teams.members`.** `players.teamId` is a
denormalised cache written *after* the team update; the reconciler (hourly job)
fixes drift. This avoids needing multi-document transactions for the common
case.

### `matches`

```json
{
  "_id": "m_7f3a…",                  // matchId generated by hub at room creation (idempotency key)
  "mode": "teams2", "roomId": "arena-2:room-5", "startedAt": ISODate, "endedAt": ISODate,
  "tournamentId": ObjectId | null, "bracketMatchId": "r2-m3" | null,
  "result": { "winnerTeam": 1, "scores": { "1": 4200, "2": 3100 } },
  "players": [ { "playerId": ObjectId, "team": 1, "kills": 12, "deaths": 3, "score": 18500, "level": 45,
                 "damage": 51000, "xpAwarded": 900, "coinsAwarded": 120, "ratingDelta": +14 } ],
  "v": 1
}
```

Index: `{ "players.playerId": 1, "endedAt": -1 }`, `{ tournamentId: 1 }`,
TTL index on `endedAt` (e.g. 90 days) if you do not want to keep history forever.

### `match_results_applied`

`{ _id: "m_7f3a…:playerId" }` — written in the same operation sequence as the
player update; a duplicate result from the queue hits the unique `_id` and is
skipped. This is the dedupe ledger.

### `ledger` (economy audit log)

```json
{ "_id": ObjectId, "playerId": ObjectId, "at": ISODate, "type": "PURCHASE" | "REWARD" | "ENTRY_FEE" | "REFUND",
  "ref": "shop:eq_barrel_steel" | "match:m_…" | "tourney:…", "delta": { "coins": -500 }, "balanceAfter": { "coins": 12000 },
  "idem": "purchase:playerId:clientTxnId" }
```

Unique index on `idem`. Every wallet change writes a ledger row.

### `leaderboard_snapshots`

Periodic (every 5 min) top-1000 dumps per board from memstore, plus final
season standings. Used for restore after memstore loss and for history UI.

Static catalogs (`items.json`, `tanks.json`, `shop.json`, `boosts.json`) are
**files** shipped with the build, not collections: they are versioned with the
code and loaded at boot. Put only mutable, per-player, per-team data in Mongo.

## 2. Write patterns

### Applying a match result (hub `ResultApplier`)

```java
void apply(MatchResult r) {
    for (PlayerResult p : r.players) {
        String key = r.matchId + ":" + p.playerId;
        try { applied.insertOne(new Document("_id", key).append("at", now)); }
        catch (MongoWriteException dup) { continue; }              // already applied → idempotent skip
        players.updateOne(eq("_id", p.playerId), combine(
            inc("progress.accountXp", p.xpAwarded),
            inc("wallet.coins", p.coinsAwarded),
            inc("stats.kills", p.kills), inc("stats.deaths", p.deaths), inc("stats.matches", 1),
            max("stats.bestScore", p.score),
            inc("stats.byMode." + r.mode + ".kills", p.kills)));
        ledger.insertOne(rewardRow(p, r));
        levelUpCheck(p.playerId);                                   // separate read+update; safe to redo
    }
    matches.replaceOne(eq("_id", r.matchId), r.toDocument(), new ReplaceOptions().upsert(true));
    leaderboards.apply(r);                                          // memstore ZADDMAX / ZINCRBY
}
```

Order: ledger-of-applied first (so a crash mid-way leaves a player *not*
rewarded rather than double-rewarded), then `$inc`s. A crash between the
ledger insert and the update loses one reward — log the key in `applied`
with `"done": false` and flip it at the end; a recovery pass reapplies rows
with `done == false`.

### Purchases (no double spend)

```java
UpdateResult u = players.updateOne(
    and(eq("_id", pid), gte("wallet.coins", price)),
    combine(inc("wallet.coins", -price), push("inventory", itemDoc)));
if (u.getModifiedCount() == 0) throw new InsufficientFunds();
ledger.insertOne(purchaseRow);   // idem unique index catches client retries
```

Single-document atomicity is all we need: balance check and deduction happen in
one `updateOne` with a filter.

### Team membership

Join: `updateOne({_id: teamId, "members.playerId": {$ne: pid}, $expr: {$lt: [{$size: "$members"}, "$capacity"]}}, {$push: {members: …}})`;
if modified, `updateOne(players, {_id: pid, teamId: null}, {$set: {teamId}})`. If the
second write fails, the hourly reconciler repairs it from `teams.members`.

Role changes and leadership transfer are single team-document updates with a
filter asserting the caller's current role (`"members": {$elemMatch: {playerId: caller, role: "LEADER"}}`).

## 3. Read patterns

- Player login: one `findOne` by username → session in memstore. Profile is
  then cached in memstore (`HSET player:{id}` … `EX 3600`) and served from
  there for lobby reads; writes go to Mongo first, then invalidate/refresh the
  cache (`DEL player:{id}`).
- Join ticket: hub reads player doc (or cache), resolves equipment + active
  boosts into a flat modifier list, writes ticket to memstore. Arena never
  sees Mongo documents.
- Leaderboard pages: memstore `ZREVRANGE` for live boards; Mongo snapshots for
  past seasons.

## 4. Schema evolution

Every document carries `v`. Readers upgrade lazily (`PlayerCodec.decode`
handles all past versions; on next write the doc is saved as current). Never
run a blocking migration over `players` during play hours.

## 5. Backups and sizing

- `mongodump --oplog` nightly to a second disk, keep 14 days; test a restore
  monthly.
- Expected sizes: player doc ~2–5 KB → 1 M players ≈ 5 GB; matches at 3 KB ×
  50 k/day ≈ 150 MB/day (TTL 90 days ≈ 13 GB). WiredTiger cache 8 GB covers the
  hot set.
- Run `mongod` with `--wiredTigerCacheSizeGB 8`, journal enabled, on its own
  disk/partition if possible, THP disabled.
